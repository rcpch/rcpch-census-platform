# Database Seeding and Publication

Because the database for this project is large (>5Gi), the recommended workflow is to seed and dump the database locally after making changes, then publish the dump as a GitHub release. This ensures reliable, versioned, and reproducible deployments.

## Why Local Dumping?

- Cloud-based dumps/uploads of large databases are slow and error-prone.
- Local seeding and dumping allows for rapid iteration and testing.
- The dump is tested before publication, ensuring it can be restored cleanly.

## Workflow Overview

1. **Seed and update the database locally** using your Django app and scripts.
2. **Build a compressed dump** using the provided convenience script.
3. **Test the dump** to ensure it restores cleanly.
4. **Publish the dump** as a GitHub release using another script, with automatic versioning and split support for large files.

## Step-by-Step Instructions

### 1. Build the Database Dump

Run the following command from the project root:

```bash
./s/build-dump
```

This script will:

- Start a local PostGIS container for building the dump.
- Build and run the Django seeder image to migrate and seed the database.
- Create a compressed dump file in `postgis_dump_files/rcpch-census.dump`.
- Test the dump by restoring it in a fresh container.
- Clean up containers.
- Prompt before overwriting any existing dump.

### 2. Release the Dump to GitHub

After building the dump, run:

```bash
./s/release-dump
```

This script will:

- Check for the dump file (or prompt to build it).
- Authenticate with GitHub CLI (`gh`).
- Suggest a new version number based on previous releases.
- Optionally split the dump if it exceeds 1.8GB (to fit GitHub's upload limits).
- Prompt for release notes and type.
- Create a GitHub release and upload the dump (or split parts).
- Provide instructions for reassembling split files if needed.

### 3. Downloading and Using the Dump

See the release notes generated by `s/release-dump` for instructions on downloading, reassembling (if split), and restoring the dump in Docker or locally. Example one-liner for reassembly:

```bash
for part in {a..z}; do
  wget -q https://github.com/rcpch/rcpch-census-platform/releases/download/<VERSION>/rcpch-census-<VERSION>.dump.part-a${part} 2>/dev/null || break
done
cat rcpch-census-<VERSION>.dump.part-* > rcpch-census-<VERSION>.dump
rm rcpch-census-<VERSION>.dump.part-*
```

## Notes

- The dump file is gitignored and should not be committed.
- Always use the scripts for consistency and to ensure the dump is tested before release.
- After updating the dump and redeploying, invalidate CDN caches as needed.

## Troubleshooting

- If the dump or restore fails, check the logs for errors and ensure your local environment matches the production schema and extensions.
- For very large dumps, ensure you have sufficient disk space and memory locally.
